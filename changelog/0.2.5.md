## Highlights

### Generated tests for XML responses no longer trip XXE checks — and actually assert repeated elements

For a contract whose response body is XML, the generated test used to build a bare
`DocumentBuilderFactory` and parse the response with it. SpotBugs / find-sec-bugs flagged
`XXE_DOCUMENT` in every generated test class, and there was nothing you could do about it
short of editing generated code.

**Generated tests now parse the response with `ContractVerifierUtil.parseXml(...)`**, which
rejects DOCTYPE declarations, disables external general / parameter entities and external
DTD loading, turns off XInclude and entity-reference expansion, and enables
`FEATURE_SECURE_PROCESSING`:

```java
Document parsedXml = parseXml(response.getBody().asString());
```

Regenerate your tests to pick this up. A response body that declares a DOCTYPE now fails
the generated test.

**Repeated parent elements are now indexed on the element that repeats.** For a body like
a sitemap, with several `<url><loc>…</loc></url>` entries, the generator emitted
`/urlset/url/loc[2]/text()` and an expected value of `""` — an XPath that matches nothing,
compared to an empty string, so entries 2..N passed whatever the producer returned. The
generated assertions are now:

```java
assertThat(valueFromXPath(parsedXml, "/urlset/url/loc/text()")).isEqualTo("https://a");
assertThat(valueFromXPath(parsedXml, "/urlset/url[2]/loc/text()")).isEqualTo("https://b");
```

A positional index is added at every level where an element repeats among its siblings, so
nested repeats (`/root/a[2]/x[2]/text()`) and attributes of repeated elements
(`/root/item[2]/@id`) are addressed correctly too. Tests regenerated from such contracts may
now fail where they previously passed silently — that is the bug being fixed.

The same XPath fix applies to **WireMock stubs generated from XML request bodies**: a request
with repeated parent elements produced `matchesXPath` patterns such as
`/urlset/url/loc[2]/text()` = `""`, which select nothing, so the stub never matched the very
request the contract described. Regenerate your stubs to pick this up.

### `XmlAssertion.assertThat(String)` no longer resolves external entities

`XmlAssertion` (both `stubborn-contract-xmlassert` and the copy in the verifier) parsed its
input with PsychoPath's `XercesLoader`, which turns off loading an external DTD but still
resolves entities declared in an internal subset. An XML body containing
`<!DOCTYPE x [<!ENTITY e SYSTEM "file:///etc/passwd">]>` had that file's contents expanded
into the document. Parsing now uses the same hardened settings as `parseXml` above, and a
body with a DOCTYPE fails with `IllegalStateException`.

### Typed assertions for Avro messages (incubating)

A generated messaging test compares the received body as JSON, and JSON has fewer types
than Avro. A producer that changed `createdAt` from a `timestamp-millis` `long` to a
`string` still passed, as long as the text was the same.

**With `assertAvroTypes` turned on, a messaging contract that declares
`metadata.kafka.avro.schema` reads the received record with that schema**, under the same
schema resolution rules Schema Registry applies, and then checks each value the contract
names:

```java
GenericRecordAssert avroRecord = assertThatAvro(response.getPayload()).readWith("{...}");
avroRecord.field("createdAt").isEqualTo(1700000000000L);
```

A producer change the consumer can still read passes; any other change fails, naming the
field. Records, arrays, maps, unions, enums, logical types and `SpecificRecord` payloads are
covered, and body matchers (`byRegex`, `byType`, …) work as they do for JSON. The switch is
off by default, so existing contracts generate the same tests as before.

Two limits to know:

* Values are compared only for the fields the contract body names.
* The received payload must be an Avro `GenericRecord`. The stock receivers return raw bytes
  for an Avro message, so configure a receiver that deserializes Avro.

See the how-to guide *How Can I Verify an Avro Message the Way Its Consumer Reads It?* for setup.
