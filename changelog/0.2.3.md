## Highlights

### Contracts installed in a split local repository are found again

Maven's [split local repository](https://maven.apache.org/resolver/local-repository.html#split-local-repository)
(`-Daether.enhancedLocalRepository.split=true`) installs artifacts under an `installed`
prefix, so a contracts JAR lands in
`<local-repository>/installed/com/example/contracts/1.0.0/`. The Maven plugin never looked
there. `mvn install` on the contracts module succeeded, and the producer then failed:

```
No stubs or contracts were found for [com.example:contracts:1.0.0:]
```

**With `contractsMode` `LOCAL`, contract resolution now goes through the local repository
manager Maven itself is configured with**, so the layout Maven installs into is the layout
Stubborn reads from — split or not, and whatever prefixes you have configured.

The plugin was building its resolver session from scratch, and that session carried none of
the resolver configuration Maven seeds from the command line, so its local repository
manager was created with the split disabled while Maven's own was not. The `generateTests`
and `convert` goals now hand the session Maven injects to the stub downloader instead. Two
consequences worth knowing:

* An obsolete copy of the same coordinates left over in the old unsplit layout can no
  longer win. Only the configured layout is searched, which is what Maven does for every
  other dependency in your build.
* `REMOTE` mode is unchanged. It still resolves into a temporary local repository, so
  verifying contracts from a remote repository does not write into your `~/.m2`.

Outside Maven — standalone Stub Runner, the Gradle plugin — the session Stubborn builds for
itself now applies the `aether.*` system properties as resolver configuration, so the same
layout settings are honoured there too.

Reported with a minimal reproducer by
[@ascheman](https://github.com/ascheman)
([#266](https://github.com/stubborn-sh/stubborn-contract/issues/266)), who also found the
masking case: an older artifact in the unsplit layout made the failure look intermittent.

### REST Docs stubs match the request they documented

`WireMockSnippet` built its query matchers out of the raw query string, so a documented
request to `?sort=externalId,asc` wrote the value still percent-encoded:

```json
"queryParameters": { "sort": { "equalTo": "externalId%2Casc" } }
```

WireMock compares query parameters against their **decoded** values, so that stub never
matched the request the test had just sent. Any value with a reserved or escaped character
was affected, parameter names included, and a value containing an `=` of its own was cut at
the first one. **A stub generated from a REST Docs test now matches that test's own
request.**

The query is split with WireMock's own parser, `Urls.splitQuery` — the code the server runs
while matching an incoming request — rather than with `URLDecoder`. That difference is not
cosmetic: WireMock leaves the `+` of an ISO offset date-time alone, where `URLDecoder` would
turn `?from=2020-01-01T00:00:00+01:00` into a space and miss all over again.

`WireMockHttpRequestAdapter`, which presents a WebTestClient exchange to WireMock during
`verify()`, encoded query values the same way and had a second bug of its own: it split the
query with a helper that returns `null` when the delimiter is absent, so a single-parameter
query left every query matcher to throw a `NullPointerException` inside WireMock. It uses
the same parser now.

Reported by [@marcin-obenan](https://github.com/marcin-obenan)
([#265](https://github.com/stubborn-sh/stubborn-contract/issues/265)). If you worked around
it by stating the decoded matcher yourself through
`WireMockRestDocs.verify().wiremock(...)`, you no longer need to.

### A samples bump that does not happen no longer reports success

Internal to the release process, and the reason the 0.2.2 samples stayed pinned to 0.2.1
while the release looked green: the step that asks `stubborn-samples` to pin itself to a new
release swallowed a failed dispatch and a missing token, and exited 0 either way. It now
fails loudly — and the release step is marked `continue-on-error`, so a published release is
never failed retroactively by a bump that could not be dispatched, but it does not look like
it worked either.

## Upgrading from 0.2.2

Nothing to do. Both user-facing changes are bug fixes; no API, property or configuration
changed, and nothing you resolve today moves.
