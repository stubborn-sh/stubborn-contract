## Highlights

### Jetty: the BOM now follows Boot instead of overriding it

0.2.0 narrowed the consumer BOM so it stopped managing versions Spring Boot owns — with one
exception, Jetty, which it held on the 12.0.x line. That exception was a mistake, and the
reasoning given for it was wrong. **A `spring-boot-starter-jetty` application and Stubborn's
stub runner now work together, with nothing to configure.**

Jetty 12 is one product published under several groupIds. `spring-boot-dependencies` imports
`jetty-bom` and `jetty-ee11-bom`, so Boot manages the core and the Jakarta EE 11 layer — but
**not** `org.eclipse.jetty.ee10`, which is the servlet layer `wiremock-jetty12` is built
against. Nothing was managing `ee10`, so it resolved to the 12.0.30 `wiremock-jetty12`
declares while Boot pulled the core to 12.1.x. Mixing minor lines resolves cleanly and fails
later, at runtime, because `jetty-ee10-servlet`'s own `ServletContextHandler` calls
`Environment.ensure` in its static initializer and that signature changed between the lines:

```
NoSuchMethodError: org.eclipse.jetty.util.component.Environment.ensure(java.lang.String)
```

0.2.0 "fixed" that by pinning every `org.eclipse.jetty` artifact down to 12.0.x — which
cured the skew by dragging the application's Jetty down with it, and left Boot's `ee11`
layer at 12.1.x on top of a 12.0.x core, so the application stopped starting instead.

This release manages **only `org.eclipse.jetty.ee10`, at the Jetty version Boot already
uses**. Core Jetty and `ee11` are left to Boot, in the consumer BOM and in Stubborn's own
build alike. Nothing here can change a version your platform BOM has chosen; it fills the
gap Boot leaves rather than winning an argument with it.

If you added the `jetty-ee10-bom` import as a 0.2.0 workaround, you can drop it.

Fixes [stubborn-sh/stubborn#142](https://github.com/stubborn-sh/stubborn/issues/142), and
thanks to [@mhalbritter](https://github.com/mhalbritter), who tried the `ee10` import,
showed it works, and so disproved the claim the 0.2.0 notes were built on.

## Upgrading from 0.2.0

**Your stub runner and your Jetty application now share Boot's Jetty 12.1.x.** For most
projects that is the whole of it: delete any `jetty-ee10-bom` import or
`org.eclipse.jetty` exclusion you added to work around 0.2.0 and nothing else changes.

### One behaviour change to know about: `Content-Type` charset case

Because the stub server now runs on Jetty 12.1 rather than 12.0, this is worth checking if
your contracts match a `Content-Type` that carries a charset.

Jetty 12.1's `HttpParser` normalises the charset parameter of a known header to lower case
before WireMock ever sees it. A client sending

```
Content-Type: application/json;charset=UTF-8
```

is read by the stub server as `application/json;charset=utf-8`. A contract that declares the
upper-case form produces an `equalTo` matcher for the upper-case form, which no longer
matches a live request:

```
Content-Type: application/json;charset=UTF-8   |   Content-Type: application/json;charset=utf-8   <<<<< Header does not match
```

This affects a header matcher compared verbatim against a real request. It does not affect
the response side, which WireMock emits rather than matches, and it does not affect
generated test code that merely asserts a header string.

If a stub stops matching after upgrading, declare the charset in lower case in the contract:

```java
r.headers((h) -> h.header("Content-Type", "application/json;charset=utf-8"));
```

Nothing needs to change on the client: it may keep sending upper case, since Jetty
normalises what arrives.
