## Highlights

### The BOM now manages every REST Assured module a generated test can need

A generated contract test is compiled against REST Assured, and which module it needs is
decided by the plugin's `testMode`: `spring-mock-mvc` for `MOCKMVC`, `spring-web-test-client`
for `WEBTESTCLIENT`, `rest-assured` itself for `EXPLICIT`. Spring Boot manages none of them,
and until now `stubborn-contract-dependencies` managed only `rest-assured`. **Switching `testMode` to `WEBTESTCLIENT` no longer means hunting down a
version.**

`stubborn-contract-starter-verifier` brings `rest-assured` and `spring-mock-mvc`, so the
default mode always worked. On `WEBTESTCLIENT` the generated test needs
`spring-web-test-client`, which the starter does not bring — it would drag WebFlux onto the
test classpath of every consumer, including the majority on MockMvc — so you declare it
yourself. That declaration then failed to resolve, with the BOM imported and
`spring-boot-starter-parent` on top:

```
'dependencies.dependency.version' for io.rest-assured:spring-web-test-client:jar is missing.
```

All three modules are now managed, at the one `rest-assured.version` Stubborn builds against,
so the dependency your `testMode` needs resolves without a `<version>`:

```xml
<dependency>
    <groupId>io.rest-assured</groupId>
    <artifactId>spring-web-test-client</artifactId>
    <scope>test</scope>
</dependency>
```

One version for all three is deliberate, not tidiness: they share internals and are not
supported mixed across versions.

This is the kind of entry the narrow-BOM rule from 0.2.0 is *for*, not an exception to it.
That rule is that the BOM manages Stubborn's own artifacts plus only the third-party ones
that are part of Stubborn's API surface and that Boot does not manage — and a module the
generated test will not compile without is exactly that. A consumer still cannot have a
version of anything Boot manages replaced by importing this BOM.

Fixes [stubborn-sh/stubborn#147](https://github.com/stubborn-sh/stubborn/issues/147), reported
by [@mhalbritter](https://github.com/mhalbritter) from the start.spring.io integration.

### Documentation: what the BOM manages, corrected

The installation, Maven plugin and migration pages still described the BOM as it was before
0.2.0 — managing `spring-cloud-stream`, `spring-cloud-stream-test-binder` and the Spring Boot
4.x split modules `spring-boot-restclient` / `spring-boot-http-client`. It has managed none of
those since 0.2.0 narrowed it ([#142](https://github.com/stubborn-sh/stubborn/issues/142)), and
the Maven plugin page also quoted a REST Assured version two releases stale.

Those pages now list what the BOM actually manages — Stubborn's own artifacts, WireMock, the
three REST Assured modules, and the `org.eclipse.jetty.ee10` servlet layer at the Jetty version
Boot already uses — and say plainly that it manages nothing Boot manages, so import order
cannot change your platform's versions.

The getting-started and Maven plugin pages now also name the REST Assured module that goes with
each `testMode`, which is the thing #147 had to be worked out from first principles. The
getting-started page additionally called the JAX-RS mode `JAXRS`; it is `JAXRSCLIENT`.

## Upgrading from 0.2.1

Nothing to do. The change adds two entries to the consumer BOM's `dependencyManagement` and
removes nothing, so no version you resolve today moves.

If you pinned `io.rest-assured:spring-web-test-client` or `:spring-mock-mvc` by hand to work
around this, you can drop the `<version>` — but leaving it in place is harmless, since your own
declaration still wins over the BOM.
